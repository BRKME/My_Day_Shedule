# My_Day_Shedule

Персональный трекер дня в Telegram: утром присылает план, вечером — задачи
на вечер, задачи отмечаются кнопками прямо в сообщении, прогресс копится
в статистике с уровнями (Хаос → Абсолютный контроль → Легенда).

## Архитектура

Два процесса, общий репозиторий как база данных:

```
VPS cron (07:30 / 11:00 / 19:00 MSK)
   └─ dispatch.sh ──> workflow_dispatch ──> GitHub Actions
                                              └─ notifier.py  → Telegram (сообщение с кнопками)
                                                              → stats.json (задачи дня)

VPS systemd (myday-bot.service)
   └─ tracker_bot.py ← нажатия кнопок ← Telegram
                     → stats.json, message_states.json → коммит в репозиторий
```

| Файл | Роль |
|------|------|
| `core.py` | общая логика обоих процессов: формат задач, уровни, слияние статистики, прополка состояний, загрузка расписания |
| `notifier.py` | GitHub Actions: собирает и отправляет сообщения по периодам |
| `tracker_bot.py` | VPS: обрабатывает нажатия, считает статистику, синкает состояние |
| `data/schedule.json` | недельное расписание задач — правится руками |
| `data/kids_schedule.json` | занятия детей по дням |
| `stats.json` | статистика по дням (источник истины — локальный файл на VPS) |
| `*.html` + `*.mp3` | страницы-эссе на GitHub Pages, по одной в будний день |
| `message_states.json` | состояния активных сообщений, прополка до 20 свежих |

### Почему расписание в JSON, а не в коде

Правка расписания — правка данных. Ошибка в JSON ловится тестами
(`tests/test_schedule_data.py`), а не обнаруживается утром по пустому
сообщению. Незакрытый `<i>` проверяется отдельно: Telegram отвергает
сообщение с битым HTML целиком.

### Почему не YAML

`tracker_bot` живёт в systemd на голом окружении VPS. JSON — stdlib,
нулевой риск, что деплой упадёт на отсутствующей зависимости.

## Страницы-эссе

Пять страниц на GitHub Pages: молитва, карьера, Талеб, Экклезиаст,
Стоицизм. Утреннее сообщение несёт **одну** — ссылкой в тексте и кнопкой.

Колода из всех пяти ложится на рабочую неделю и тасуется заново каждую
неделю: за год ровно по 52 показа у каждой, повторов подряд и через день
нет. В субботу и воскресенье страницы нет вовсе.

Выбор детерминирован от даты (`core.page_of_the_day`), а не случаен в
момент вызова: текст и клавиатура собираются раздельно, иначе в тексте
оказалась бы одна страница, а на кнопке другая. Новая страница
добавляется одной строкой в `core.PAGES`.

## Утренние картинки

Пул — папка `morning_images/`, список тянется через GitHub API при каждой
отправке: новый файл попадает в ротацию без правки кода. При недоступности
API работает fallback-список.

## Кроны

GitHub `schedule` не используется: дрейф доходил до 4+ часов (инцидент
06.07.2026 — день пришёл дважды вместо утра и дня). Расписание держит
VPS-крон, GitHub Actions только исполняет `workflow_dispatch`.

## Запуск

```bash
pip install -r requirements.txt -r requirements-dev.txt

# уведомление вручную
TELEGRAM_TOKEN=... TELEGRAM_CHAT_ID=... python notifier.py morning   # morning|day|evening|pullups

# бот
TELEGRAM_TOKEN=... TELEGRAM_CHAT_ID=... GITHUB_TOKEN=... python tracker_bot.py

# тесты
python -m pytest tests/ -q
```

Автодеплой на VPS: `/opt/myday/autoupdate.sh` тянет репозиторий каждые 30 мин.

## Инварианты (ломать нельзя)

`tracker_bot` парсит и редактирует уже отправленный текст, а прогресс хранит
**по индексам строк**. Отсюда:

- строки задач начинаются с `• `;
- заголовки секций содержат маркеры `Вечерние задачи` / `Нельзя делать`;
- число и порядок задач в сообщении неизменны после отправки;
- строки шапки не начинаются с `📊` (такие чистятся как старые прогресс-бары);
- граница утро/день — маркер `Читать 📖 в дороге`, в субботу `Включи 🧠 Мозг`
  (`core.MORNING_BOUNDARIES`).

## Эксплуатация

**Стата — локальный файл на VPS.** GitHub — реплика и может отставать. При
конфликте дня побеждает локальная запись (`core.merge_stats`): 16.07 синк
умер с отзывом PAT, и старая логика откатила бы прогресс при рестарте.

**Состояния сообщений пропалываются до 20.** Telegram не даёт редактировать
сообщение старше 48 часов, поэтому более старые состояния бесполезны. Без
прополки файл рос бесконечно (383 КБ) и целиком уезжал в каждый коммит.

**История репозитория.** До 04.08.2026 раздутые состояния коммитились
месяцами, `.git` весит ~17 МБ. Рост остановлен; сжатие истории потребует
`git filter-repo` + force-push и делается отдельно и осознанно.

## Разработка

**Перед любыми изменениями — `docs/OPERATING_POLICY.md`.** Там правила,
нарушение каждого из которых уже приводило к инциденту, и чек-лист перед
коммитом. Если правка противоречит политике — политика обновляется тем же
коммитом.

Методология работы — `superpowers-methodology/SKILL.md` (brainstorming →
план → TDD → верификация). Для веб-страниц — `design-system/SKILL.md`.
